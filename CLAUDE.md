# ПРАВИЛА РАБОТЫ С ТОКЕНАМИ — WB-SAAS

## КРИТИЧЕСКОЕ ПРАВИЛО №1 — app.py

Файл `app.py` в корне проекта — монолит объёмом ~10 771 строка / 662 КБ (~165 000+ токенов
при полном чтении). Это ОДИН файл способен съесть весь дневной/сессионный лимит за одно
действие.

СТРОГО ЗАПРЕЩЕНО читать app.py целиком командой Read без диапазона строк.

Обязательный порядок действий при любой задаче, касающейся app.py:
1. Сначала используй `grep -n "нужная_функция\|нужный_класс" app.py`, чтобы найти номер строки.
2. Читай ТОЛЬКО нужный диапазон: `Read app.py, offset=N, limit=150` (или используй
   встроенный line-range параметр инструмента чтения).
3. Если задача требует понять общую структуру файла — используй
   `grep -n "^def \|^class \|^@app.route" app.py`, чтобы получить оглавление без полного чтения.
4. Никогда не открывай app.py "чтобы понять контекст" — сначала сформулируй конкретный
   вопрос (какая функция/роут/класс), потом ищи точечно.

Если задача объективно требует прочитать больше 30% файла за одну сессию —
останови работу и сообщи об этом явно, прежде чем продолжать. Это сигнал,
что файл пора рефакторить.

## КРИТИЧЕСКОЕ ПРАВИЛО №2 — архивные файлы

Файлы `app_backup*.py` (app_backup12.py … app_backup25.py и любые новые с этим
паттерном) НЕ являются рабочим кодом. Они должны находиться в `_archive/` и
ИГНОРИРОВАТЬСЯ при любом поиске, grep, find по проекту.

Если видишь такие файлы в корне проекта (не в _archive/) — не читай их,
сообщи, что они не убраны, и предложи переместить:
```
mkdir -p _archive && mv app_backup*.py _archive/
```

При любом `grep -r` или `find .` по проекту явно исключай:
```
grep -r "..." . --exclude-dir=_archive --exclude="app_backup*"
find . -not -path "*/_archive/*" -not -name "app_backup*"
```

## ПРАВИЛО №3 — старт новой сессии

В начале КАЖДОЙ новой сессии в этом проекте, прежде чем брать задачу в работу:
1. Не читай app.py и pdf_auto.py (4318 строк) целиком "для разогрева" —
   жди конкретную задачу.
2. Если пользователь не указал файл явно — сначала спроси или используй
   grep, чтобы локализовать нужный участок кода.
3. В конце сессии, если она длится больше ~1.5 часов активной работы,
   предложи пользователю выполнить `/compact` вручную, не дожидаясь
   автоматического порога.

## ПРАВИЛО №4 — безопасность (не про токены, но важно)

Пароль от Postgres сейчас хранится открытым текстом в `.claude/settings.json`.
Если работаешь с этим файлом — напомни пользователю вынести пароль в
переменную окружения (.env) и явно добавить `.claude/settings.json` в
.gitignore. Не выводи содержимое пароля в чат/логи без необходимости.

## ПРАВИЛО №5 — компакция

Рекомендованная частота ручного `/compact`: примерно раз в 1.5–2 часа
непрерывной работы, или сразу после завершения крупного этапа задачи
(например, после деплоя, после написания и проверки одной фичи).
Не жди автоматического срабатывания — на монолитном проекте это может
произойти слишком поздно, потеряв важный контекст текущей задачи.

## Что реально в проде

Прод — это **монолит `app.py`** (~10.8k строк), задеплоенный на Railway. `Procfile`:
`web: pip install -r requirements.txt && python3 app.py`. Веб-сервер — стандартный
`http.server.BaseHTTPRequestHandler` (не FastAPI, не Flask). БД — PostgreSQL (Railway), доступ
напрямую через `psycopg2`, без ORM. Стек: Python 3.9 локально / `venv311` для запуска,
`anthropic>=0.40.0` (Claude), MPStats API, `aiogram==3.13.0`, `reportlab`+`matplotlib` для PDF.

| Файл | Роль |
|------|------|
| `app.py` | монолит: HTTP-сервер, бизнес-логика, все продовые эндпоинты |
| `pdf_auto.py` (~4.3k строк) | генерация PDF-отчётов, ReportLab |
| `telegram_bot.py` | Telegram-бот, aiogram 3.13 |
| `niche_updater.py` | обновление одной ниши по запросу (on-demand) |
| `update_niches.py` | bulk-обновление всех ниш (cron) |
| `sourcing_intel.py` | логика выбора поставщиков по странам |
| `support_knowledge.py` | база знаний AI-агента поддержки |
| `warehouse_monitor.py` | агент мониторинга атак на склады WB (Railway cron, 4ч) |
| `create_warehouse_status.py` | идемпотентный скрипт создания таблиц `warehouse_status`/`warehouse_monitor_log` |
| `miniapp/` | Telegram Mini App (HTML/CSS/JS) |
| `requirements.txt` | зависимости `app.py` |
| `requirements-monitor.txt` | зависимости `warehouse_monitor.py` (без reportlab/matplotlib/aiogram) |

Railway — два сервиса из одного репо, разный Root Directory/конфиг:
- `wb-analyzer-production.up.railway.app` — основной, `app.py`
- `trustworthy-presence` — `warehouse_monitor.py`, cron каждые 4 часа

### PDF-отчёты — три уровня
- **Basic** (бесплатно) — вердикт AI, ключевые метрики ниши, 2 графика
- **Standard** (2500₽) — + мастер-анализ, топ-20 товаров, юнит-экономика, рекламная стратегия, сезонный план
- **Deep** (6000₽) — + топ-10 конкурентов, поставщики, документы WB, стратегия FBO/FBS, карточка товара, 90-дневный план

## `backend/` — отдельный, НЕ задеплоенный сервис

В репозитории также есть `backend/` — полноценная FastAPI-архитектура (api/v1, core/config.py,
core/deps.py, core/database.py, models/pg, models/ch, services/scraper, services/analytics,
services/pricing, services/decision_engine, services/recommendations, workers/main.py — именно
её раньше по ошибке описывали как архитектуру всего проекта).

Это не заброшенный шаблон и не фикция — там реализован рабочий PDF-export endpoint
(`POST /api/v1/analysis/category/export-pdf`, basic/standard/deep, MPStats-first с fallback на
scraper, есть тесты и `.github/workflows/ci.yml`). Последний коммит в `backend/` — 2026-06-12
(`feat-pdf-deep-complete`), т.е. это активная ветка разработки, которая on hold, а не мёртвый код.

**Ключевое:** `backend/` **не подключён к Procfile** и не деплоится на Railway — это не то,
что видят пользователи. `app.py` в проде дергает его как "Прокси к FastAPI backend (оставлен для
совместимости)" (см. `app.py:9444`) — деталь совместимости, не факт что путь реально используется.

Если ставится задача по PDF/декижн-инжину/аналитике — **сначала уточнить**, идёт ли речь про
прод (`app.py`/`pdf_auto.py`) или про `backend/` (экспериментальный сервис). Не предполагать
автоматически.

## Правило работы с .env и секретами

**НИКОГДА** не выводить полные значения переменных из `.env` в чат, результаты команд или логи видимые пользователю. Это касается API-ключей, токенов, паролей, строк подключения к БД.

**Разрешено — только маскированный вывод:**
- Имя переменной
- Статус: ✅ есть / ❌ отсутствует
- Маскированное значение: первые 8 символов + `...` + последние 4 символа

**Правильный способ проверки переменной:**
```bash
grep "^VARIABLE_NAME" .env | sed -E 's/^([^=]+=.{8}).*(.{4})$/\1...\2/'
```

```python
key = os.getenv('VARIABLE_NAME')
if key:
    print(f"VARIABLE_NAME: {key[:8]}...{key[-4:]} ✅ (длина: {len(key)})")
else:
    print("VARIABLE_NAME: ❌ отсутствует")
```

**Запрещено:** `cat .env`, `grep` без маскирования, любой вывод целого значения ключа.

## Правило использования PostgreSQL MCP

При работе с PostgreSQL MCP (прямые SQL-запросы в разговоре, не через файлы-скрипты):

- **РАЗРЕШЕНО:** SELECT-запросы любой сложности для диагностики, просмотра данных, подсчёта строк, поиска аномалий
- **ЗАПРЕЩЕНО** без явного письменного запроса пользователя в том же сообщении: `UPDATE`, `DELETE`, `DROP`, `ALTER`, `TRUNCATE`, `INSERT`
- Если нужно изменить данные — предложить пользователю SQL-команду текстом и спросить подтверждение, либо оформить как отдельный `.py` скрипт с возможностью review перед запуском (как было раньше: `/tmp/fix_xxx.py`)
- Это правило защищает от случайного повреждения продакшен-данных через разговорный SQL-доступ
